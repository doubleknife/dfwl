# 小程序上线前 UI/UX 现状全量审计

> 审计日期：2026-09-26。审计对象：`mini-program` 当前工作区的 **11 个实际页面**，并将发车、卸货/重量录入、OCR/库存匹配、费用审批发起等状态分支单独核查。本文件是后续移动端设计输入；本轮不修改小程序、后端、配置或测试。

## 0. 方法、证据与优先级

- 逐项阅读 `app.js`、`app.json`、`app.wxss`、全部 11 个页面的 `index.js/index.wxml/index.json`、`utils/request.js`、`utils/permissions.js`、`utils/approvalApplication.js`、`utils/business.js`；核对后端 `RouteController/RouteAccessPolicy`、`TireController/TireAccessPolicy`、`ApprovalController/ApprovalAccessPolicy/ApprovalTemplateService/ApprovalInitiationService`、`DriverSalaryController/DriverSalaryService`、`CurrentUserService` 和 `PermissionCode`。
- 这是**源码与契约审计**，没有在本轮运行微信开发者工具或真机，也没有测量实际触控命中率、户外对比度、弱网耗时。关于小字号、触控区域和单手可及性的判断来自 `rpx` 样式、组件类型与布局；需在重构验收时用常见手机和真实网络复核。
- 操作步骤数从**已经登录且位于当前页面**开始估算，只数用户必须进行的可见输入/点击，区分“进入页面”与“提交业务”；微信系统相册/相机/确认弹窗另计。某些分支随模板、数据和权限变化，故给出区间而非伪精确数字。
- `P0`＝影响正常使用、结果可能误导或极易误操作；`P1`＝明显增加司机操作和理解负担；`P2`＝视觉与体验优化。文末矩阵**每页记录一项最高优先级主问题**，计数以矩阵为准；章节中的次要问题不重复计数。
- 工作区有先前任务留下的未提交文件，本轮不回滚、不修改。文档描述当前代码；不能将隐藏入口等同于后端授权成功，也不能将后端拒绝掩盖成“没有这个功能”。

## 1. 页面清单与现有导航

`app.json` 按顺序注册以下 11 页。没有 `tabBar`；所有业务入口由 `pages/home` 的卡片和 `wx.navigateTo` 提供。`pages/route-detail` 再引向 `pages/weight`，`pages/approvals` 引向费用发起和审批详情。页面顶部沿用微信原生导航栏（深蓝背景），业务内容使用全局 `.page/.panel` 样式。

| # | 页面/文件 | 主要入口 | 页面任务 |
|---:|---|---|---|
| 1 | 登录 `pages/login/index.*` | 未登录/401 重定向 | 手机号密码登录 |

| 3 | 个人信息 `pages/profile/index.*` | 首页卡片 | 查看账号/绑定、改密、退出 |
| 4 | 我的线路 `pages/routes/index.*` | 首页“我的线路” | 查看/按状态筛选线路 |

## 2. 两类司机的真实使用路径与权限

### 2.1 自有司机（`/me.driverType = INTERNAL`，并满足对应角色权限）

登录 → `/me` → 首页显示当前车辆/绑定状态 → 我的线路（需要 `route:list`）→ 已发布线路详情 → 发车（`route:depart` 且 `RouteAccessPolicy` 确认本人线路）→ 运输中 → 毛重/皮重 → 卸货（`route:unload` 且本人线路）→ 完成后只读。工资入口要求 `salary:mine`，后端还要求确为自有司机并仅查本人。换胎入口要求 `tire:request`，后端 Policy 还检查自有司机、本人 `driverId` 与当前绑定车辆；OCR 和精确库存匹配分别使用同一权限，真正创建时仍需二次校验。

审批入口由 `approval:create`、`approval:history:view`、`approval:process`、`approval:return` 任一权限触发；自有司机能否发起费用取决于 `approval:create`、已发布且允许其角色发起的模板、模板录入/归属约束及业务资源约束。它**不由首页卡片单独决定**。司机即使获 `approval:process`/`approval:return`，后端 `ApprovalAccessPolicy.ensureCanProcess` 仍禁止处理审批。费用申请页应明确区分“无权限”“无可发起模板”“模板只允许管理端/Excel”“缺少线路/车辆资料权限”，不能只隐藏按钮。

### 2.2 外协司机（`/me.driverType = OUTSOURCED`）

登录 → `/me` → 首页人车绑定 → 我的线路 → 在授权且归属本人线路时发车/卸货 → 个人信息。首页不显示工资单、换胎或审批入口；后端分别用 `DriverSalaryService`、`TireAccessPolicy`、`ApprovalTemplateService/ApprovalAccessPolicy` 保底拒绝外协司机工资、换胎、审批发起/处理。即使错误配置了权限，也不能把这些能力当作可用。没有当前车辆时首页应明确解释发车可能受阻及联系谁处理，而不是只显示“暂无绑定”。

### 2.3 UI—后端权限/Policy 对照

| 能力 | 小程序入口/按钮现状 | 后端实际要求 | 审计结论 |
|---|---|---|---|
| 看本人线路 | 首页卡片检查 `route:list`；线路页自身不再判权限 | `route:list`；司机仅返回本人范围 | 入口与权限基本一致；直接打开页时仍依赖请求 403 提示 |
| 发车 | 线路状态为 `PUBLISHED` 即显示按钮 | `route:depart` + 本人发车范围 | **按钮没检查权限**；有列表权限、无发车权限时会出现可点但 403 的动作 |
| 卸货/录重量 | `IN_TRANSIT` 即显示入口；称重页非完成状态显示提交 | `route:unload` + 本人卸货范围 | **按钮没检查权限**；也未对取消/作废等其他状态明确禁用 |
| 本人工资 | 首页 `INTERNAL + salary:mine` | `salary:mine` + DRIVER + 非外协 + 本人 | 基本一致；页面直接进入时只通过 API 拒绝 |
| OCR/换胎 | 首页 `INTERNAL + tire:request`；页面重新检查 | `tire:request` + 非外协；创建还查本人/当前车 | 基本一致；UI 暴露可编辑车辆 ID，后端会拒绝不一致数据 |
| 费用审批发起 | 首页有审批任一权限就显示卡片；审批页发起按钮检查 `approval:create` | `approval:create` + 模板可发起角色/配置/资源条件，外协拒绝 | “有审批中心入口”不等于“能发起费用”；需显示具体可用状态 |
| 处理审批 | 审批详情按待办任务和权限显示按钮，`isDriver` 隐藏 | `approval:process`/`approval:return` + `denyAllDrivers` + 当前任务归属 | UI 与后端红线大致一致，使用 `roleCode` 包含 `DRIVER` 的宽松判断，后端是精确角色码，应统一语义 |
| 审批历史/详情 | 首页有相关权限可见，列表/详情读取 | 四种审批权限之一 + 业务可见范围 | 入口授权与详情访问仍需由后端收口；UI 应显示无权/无数据差别 |

`/me` 返回 `role.code`、`driverType`、`driverId`、`currentVehicleId`、`permissions`。`permissions.js` 的 `isDriver` 用角色码包含 `DRIVER` 判断，而后端 `CurrentUserService` 仅将角色码精确等于 `DRIVER` 的账号当司机；这是一处潜在语义差异，尤其涉及自定义角色。审计建议未来前端使用与后端一致的身份字段/判定契约，不通过错误隐藏制造简洁感。

## 3. 逐页现状、步骤与目标结构

### 3.1 登录

- **职责/入口/信息**：手机号和密码登录；未登录或 401 时进入。字段有永久可见 Label，密码遮挡，键盘类型分别为数字/默认；主按钮“登录”。成功保存 `data.accessToken` 与用户并转首页。
- **操作步骤**：填手机号 → 填密码 → 登录，**3 步**；没有重复业务输入。
- **状态与权限**：公开页；按钮显示 `loading`，请求层以 Toast 提示 HTTP/网络错误；无独立错误区、无字段内校验或明确重试说明。`login()` 没有检查当前 `loading` 防重复触发，按钮亦未显式 `disabled`。
- **移动问题**：居中卡片和 24rpx 辅助字在户外可能偏小；单手输入尚可，主按钮在表单底部，未设计固定安全区。失败只弹短 Toast，司机可能不知道手机号格式、密码错或网络断；不能把这些差异都写成“请求失败”。
- **建议**：保留单页登录、可见 Label；输入法和错误近字段呈现，登录过程禁二次提交、保留错误的可重试入口，主按钮保证 88rpx 左右触控高度与底部可及。**P1**。

### 3.2 首页工作台

- **职责/入口/信息**：登录后读取 `/me`，显示司机姓名或手机号、角色/司机类型、当前车牌/绑定状态、由 `visibleHomeCards()` 生成的两列功能宫格。点击卡片进入线路、个人信息、自有司机工资/换胎、可用审批中心。
- **操作步骤**：查看当前车 **0 步**；进入线路/工资/换胎/审批各 **1 步**；完成任务还需下一页操作。
- **状态与权限**：`onShow` 每次请求 `/me` 更新本地用户；有 `loading` 数据但 WXML 不展示 Loading。请求失败由全局 Toast 提示，旧用户/旧卡片可能继续停留，页面也没有持久错误/重试状态；未绑定仅写“暂无绑定”。角色类型直接显示 `INTERNAL/OUTSOURCED`，没给当前任务/待办。
- **移动问题**：两列宫格将所有能力等权，不回答“现在要做哪趟线路/下一步是什么”；卡片文字“进入”占据视觉但没有具体任务。卡片点击区比小按钮宽，单手尚可，但高频操作仍需多级跳转。没有横向表格；灰色 24rpx 辅助字户外可读性待实测。
- **建议**：**当前车辆/绑定状态 → 最近或待办线路及下一步主操作 → 审批/其他待办 → 少量功能入口**。外协/自有差异通过同一权限与 Policy 口径解释；非可用能力不展示，同时给缺绑定、无任务、加载失败可理解的状态。**P1**。

### 3.3 个人信息

- **职责/入口/信息**：首页卡片进入；显示姓名/手机号、角色、司机类型、当前车；改密码与退出。字段“原密码”“新密码”有可见 Label；没有列表或筛选。
- **操作步骤**：改密：输入旧密码 → 新密码 → 保存，**3 步**；退出 **1 步**，没有确认；无重复填写已知身份。
- **状态与权限**：已登录用户可进；`onShow` 读 `/me` 无页面 Loading/错误位置；改密显示按钮 loading，失败仅请求层 Toast。司机类型可能直接显示 `INTERNAL/OUTSOURCED`；`driver.phone` 实际映射对象未赋值，最终常退回 `user.phone`。
- **移动问题**：将少用的改密表单与常看的个人资料永久平铺，且“退出”使用危险红按钮与改密并列，日常查看时占屏；信息多用 24rpx 灰字。现有表单可单手填写，但密码操作是低频任务。
- **建议**：个人摘要为首页延伸；“账户与安全”进入独立区域或折叠表单，退出位于账户菜单/页底并明确；司机类型中文化。**P1**。

### 3.4 我的线路

- **职责/入口/信息**：首页卡片；状态选择器 + 线路卡片，显示线路号、状态、日期、起讫地、净重/达标。点击整卡进入详情。无表单输入。
- **操作步骤**：直接打开详情 **1 步**；按状态筛选再打开 **2 步**。
- **状态与权限**：入口要求 `route:list`，后端 `listForDriver` 限本人。客户端固定请求 `pageNo=1&pageSize=50`，然后在这 **50 条内本地筛选**；没有加载指示、页码、总数、错误保留或重试，失败只有短 Toast，空态仍可能显示“暂无线路”。筛选列表和卡片状态直接展示 `UNPUBLISHED/PUBLISHED/IN_TRANSIT/COMPLETED/VOIDED/CANCELLED`。
- **移动问题**：当本人线路超过 50 条，筛选可能错误显示“暂无线路”，这是数据完整性风险；业务状态英文化要求司机自己翻译。卡片本身触控面积充足，列表纵向而非桌面表格，方向正确；次级字 24rpx 偏小。
- **建议**：**进行中/待发车优先的任务列表 + 状态中文筛选 + 明确分页/加载更多 + 空/错误分离**。如果采用服务器筛选必须与后端列表契约对齐，绝不能只截前 50 条后宣称无结果。**P0**。

### 3.5 线路详情与发车

- **职责/入口/信息**：线路卡片进入；顶部为线路号、原始状态、起讫地、司机/车辆数字 ID、发/卸时间、毛/皮/净重、达标结果。`PUBLISHED` 时“发车”，`IN_TRANSIT` 时“卸货称重”，`COMPLETED` 时显示只读说明。
- **操作步骤**：查看 **1 次进入**；发车：点击“发车” → 系统确认弹窗点确认，共 **2 次明确动作**；卸货入口再点一次进入称重页。
- **状态与权限**：后端发车还需 `route:depart` 和本人线路 Policy；按钮只查状态，没查权限。详情请求无局部 Loading、错误区、重试；发车没有防二次点击/请求中状态。称重成功 `wx.navigateBack()` 后，详情只在 `onLoad` 拉数据，**没有 `onShow` 刷新**，可能继续显示旧的“运输中/卸货称重”，诱使再次提交。
- **移动问题**：原始状态和内部 ID 不是司机任务语言；缺显著的“下一步”。按钮在内容尾部，手机较长内容时不一定处于拇指区域；已完成状态阅读结构还以输入字段顺序呈现。无横向表格，信息密度目前中等。
- **建议**：顶部用中文状态、当前任务与一条主操作；发车按钮同时检查权限、确认时显示车牌/目的地，提交中禁重；从称重返回时刷新状态，完成后明确只读结果。主操作应在底部安全区附近可达。**P0**。

### 3.6 卸货称重/重量录入

- **职责/入口/信息**：运输中线路详情进入；输入 `grossWeight` 毛重、`tareWeight` 皮重（`type="digit"`），前端计算净重和达标状态，点击“提交卸货”。两字段永久 Label；不需再次填司机/车辆。
- **操作步骤**：输入毛重 → 输入皮重 → 查看净重/达标 → 提交 → 确认弹窗，共 **4 次必需输入/点击**，可先核算。日期无需输入。
- **状态与权限**：后端需 `route:unload` 与本人线路、有效状态；页面只在 `COMPLETED` 隐藏提交，没有直接显示权限/其他非法状态说明。校验不通过用 Toast；请求错误亦 Toast。`submit()` 在调用 `wx.showModal` 后立即进入 `finally`，**`loading` 会在用户确认、真实卸货请求结束前归零**，且开头未防重入；弱网时按钮可能恢复可点，成功/失败时机不明确。
- **移动问题**：数字键盘合适，表单不长，能单手输入；但单位未永久显示，达标结果用 22rpx Tag 户外偏小；弹窗文案“不达标仍可继续卸货”需要给出明确数值和后果摘要。按钮非固定底部。
- **建议**：**重量输入卡 → 实时净重/达标摘要 → 底部确认卸货主按钮**；明确吨/千克单位与精度，确认弹窗展示两数和净重；从点提交直到请求结束保持防重复与 Loading，字段旁说明错误。**P0**。

### 3.7 工资单

- **职责/入口/信息**：自有司机且有 `salary:mine` 才从首页可见；月份原生 `picker`、本页合计、逐条线路工资卡（线路号或 ID、金额、业务月份/日期）。金额在视觉上是小型 Tag，没有明示币种/格式。
- **操作步骤**：默认查看 **0 步**；选月份 **1 步**；列表阅读无需额外输入。
- **状态与权限**：后端 `mySalary` 还保证本人且非外协。页面固定请求第一页 100 条，并只对 `page.records` 求和作为“合计”；无分页、总条数提示。`loading` 虽设置但 WXML 没展示，失败只有 Toast，零数据与失败易混淆。
- **移动问题**：工资应先看月份，再看该月总额/各线路明细；当前合计可能仅是前 100 条且在未选月份时混合多个月份，**展示数值可能不是真实总工资**。低饱和小金额 Tag、灰色日期在户外不够醒目。
- **建议**：**月份 → 本月工资金额（大字，含币种）→ 线路/调整明细**；明确统计范围，若 API 未提供全部记录/汇总则不能把当前页求和标为“合计”。区分加载中、无工资、请求失败。**P0**。

### 3.8 审批中心

- **职责/入口/信息**：首页卡片进入；“我的申请”“待审批”“审批历史”Tab（依权限显示），申请卡展示审批号、原始状态、类型/业务类型、流程版本；有 `approval:create` 时显示“发起审批”。点击卡进入详情。
- **操作步骤**：看默认列表 **0 步**；切 Tab **1 步**；打开详情再 **1 步**；发起再 **1 步**。
- **状态与权限**：页加载 `/me` 再读审批列表第一页 100 条；后端对 scope/详情做实际范围控制。自有司机不展示待审批，外协首页不显示审批入口；页面仍应区分直接访问的无权错误。页面有持久 `error`，但无 Loading；错误时还会把列表清空并同时显示“暂无审批”，误导为无业务。每次 `onShow` 会重选默认 Tab，返回详情后当前 Tab 可能丢失。
- **移动问题**：Tab 按钮等权且没有选中态样式绑定；状态与审批类型均可能直接显示英文码，流程版本比业务事项更醒目。`审批历史` 实际映射 `DONE`，应说清其与我的申请/待我处理关系。三按钮在窄屏可能拥挤。
- **建议**：**我的申请 / 待我处理 / 已处理** 的角色化 Tab，记住当前 Tab；卡片优先展示业务名称、申请时间、状态和下一步；发起入口随真实模板资格呈现，空/错/无权各有说明。**P1**。

### 3.9 审批详情与处理

- **职责/入口/信息**：审批列表卡片进入；审批号与原始状态/类型；按版本展示每次 `businessSnapshotJson` 原始 JSON、申请图片；任务/动作时间线显示审批人 ID、原始 `actionType/status`、时间、图片；当前处理人可填备注、打回节点序号、上传动作图片并选择通过/打回申请人/打回节点。
- **操作步骤**：查看版本/时间线只需进入，图片预览每张 **1 步**；处理：可选备注/图片 → 选择处理按钮，**1–4 步**；打回节点还须手填序号。图片是“选择 → 操作时上传 → 提交”隐式过程。
- **状态与权限**：`canApprove/canReturn` 由当前待办任务 + 对应权限 + 非司机判断；后端再检查权限、司机硬限制与任务归属。提交有 `loading` 防重、上传状态文字和持久错误；详情初次加载无显性 Loading。图片下载/上传错误既 Toast 又页内错误，反馈可能重复。
- **移动问题**：原始 Snapshot JSON、审批人/业务/附件数字 ID、技术枚举要求司机/审批人理解内部模型；版本证据和动作时间线重叠显示，长审批链需大量滚动；三个处理按钮连续同级，没有明确危险/退回后果。小图/附件行用 `56rpx` 最低高度的 `.row`，触控命中区未保证 88rpx；22–24rpx 灰字在户外偏小。打回节点需输入数字序号是明显的业务操作门槛。
- **建议**：**审批摘要 → 本次待处理事项/主操作 → 版本历史和证据 → 时间线**；把 Snapshot 解析为业务字段，原始 JSON 仅高级调试；退回节点用实际节点名称选择器，三个动作分层、确认结果。图片预览明确 Loading/失败重试，附件触控区足够大。**P0**。

### 3.10 发起费用审批

- **职责/入口/信息**：审批中心“发起审批”进入；加载 `/approval-templates/available`，筛出费用/其他模板；选择模板后依配置录单条或多条费用明细、归属（线路/日常）、线路、车辆、司机、金额、业务日期、备注，能源模板再填订单号/开始时间/数量/站点 ID；按模板要求上传申请图片并提交 `/approvals`。`OTHER` 当前提示在管理端发起。
- **操作步骤**：模板 → 归属（若多选）→ 线路（若线路费用）→ 每条车辆/司机（本人自动带出）→ 金额/日期/说明 → 可选图片选择+上传 → 提交。最短约 **4–6 步**，含线路/能源/证据时约 **8–12 步以上**；多明细随条数增长。自有司机已知 `driverId/currentVehicleId` 自动带出，但线路显示选中值为 `routeId`，非司机场景车辆/司机选后也展示 ID。
- **状态与权限**：需 `approval:create`、非外协，模板须实际允许该角色、`SINGLE` 模式和业务资源。线路模板若缺 `route:list`、非司机若缺 `vehicle:list`，页面会给出错误；加载资源只取前 100 条。提交有 `loading` 防重；上传有“已选择/上传中/完成/失败”文字，但无百分比/重试入口，选择后必须再点“上传”；字段校验集中在顶部错误 + Toast，不定位具体明细。
- **移动问题**：`EXPENSE/ROUTE/DAILY`、能源时间格式 `YYYY-MM-DDTHH:mm` 和站点 ID 暴露给业务用户；多个明细长滚动，“删除”是小按钮；开始时间不是原生时间选择；提交前无简洁总额/条数/归属摘要。表单有 Label，金额用 `digit`，业务日期用原生 picker，优点应保留；但密集能源字段不适合一次铺开。
- **建议**：**选业务模板（业务名称）→ 选归属/线路 → 填明细 → 图片依据 → 提交前摘要**；已知人车自动带出并显示名称/车牌；能源时间用合适的日期时间选择组合；错误到字段/明细，上传反馈含失败重试。主提交动作在页面尾部安全区，防重复。**P1**。

### 3.11 换胎申请与 OCR

- **职责/入口/信息**：自有司机首页进入；加载 `/me` 判 `INTERNAL + tire:request` 并预填当前 `vehicleId`。一页常驻车辆 ID、确认胎号、OCR 候选、拍/选图片、上传原图、OCR 识别、确认胎号、添加轮胎和提交申请；提交前 `request-target` 精确匹配可申请库存，创建时后端再检查本人/当前车及库存状态。
- **操作步骤**：拍/选图 → 上传 → 识别 → 选候选/编辑胎号 → 确认 OCR → 自动匹配 → 添加轮胎 → 提交，**至少 7–8 次显式操作**，系统相机选择另计。虽然 `recognize()` 可以自动上传未传图片，界面又单列“上传原图”，形成重复决策。多轮胎时整链重复。
- **状态与权限**：`tire:request` + 非外协；创建要求本人司机和当前车辆，后台二次库存检查，查询成功不保证最终提交成功。`ocrStatus/ocrError/matchStatus/uploadStatus` 有状态文字，但 `ocrStatus` 不在 WXML 清晰呈现；上传/识别/确认没有统一 `busy` 防重复，上传失败后 `uploadStatus` 可能停留“上传中”；失败主要靠瞬时 Toast，`matchStatus` 才有持久说明。只有最终提交按钮有 `loading`，也没显式禁用重复点击。
- **移动问题**：`车辆 ID` 可手改，但后端只接受本人当前车辆，输入既多余又诱发 403；多按钮同级且没有“当前只做一件事”；OCR 候选“选择”使用 `size="mini"`，户外拍照和单手点击不稳；置信度原数值、轮胎 ID 不应占主要视线；确认/库存不匹配后如何继续缺清晰下一步。按钮在长页底部，可能频繁上下滚动。
- **建议**：**拍照 → OCR 候选 → 确认胎号 → 库存匹配 → 申请摘要/提交** 的状态式短页面；显示当前车牌和司机但不要求重填 ID。当前步骤唯一主操作，前步可返回；上传进度/失败/重试和弱网状态持久可见；候选整行可点，匹配失败直说原因。保留手工输入胎号与后端二次校验，不绕过库存/权限。**P0**。

## 4. 跨页面问题专审

### 4.1 全局导航与任务定位

目前是“首页两列卡片 → 页面 → 详情”的工具箱路径，没有可持续的任务入口、待办数量或清晰返回工作台的固定导航。小程序不应照搬管理端 Sidebar/表格。适合考虑 **工作台/我的线路/我的** 的轻量底部导航，审批及换胎按权限和当前业务上下文作为任务入口；不是把 8–10 个功能都压进底栏。微信原生导航栏标题应与页内标题协调，避免重复占屏。审批列表返回后重置 Tab、线路详情从称重返回不刷新，均属于“返回上下文丢失”。

### 4.2 表单、触控与重复输入

现有登录、重量、费用、换胎、改密表单多数有可见 Label，优于纯 placeholder；但换胎仍要求手改车辆 ID，审批打回需手输节点序号，费用能源明细需站点 ID 与格式化时间。能用当前司机/车辆、模板、路线数据确定的值应带出并以业务名称显示；不能要求司机记系统 ID。所有可点区域应按手机设计稿确保**约 88rpx（约 44 逻辑像素）**的最小触控高度，行内 mini 按钮改为整行或大触控区；底部主动作考虑安全区。数字、金额用合适键盘，日期沿用原生 picker，能源时间不要让用户拼 ISO 文本。表单提交前应提供简洁摘要和对象确认，字段旁显示验证原因。

### 4.3 图片、OCR 与附件

换胎图片需经历拍照、上传、识别、确认、匹配；费用图片需选图再独立上传；审批动作图片在点击通过/打回时才上传。`utils/request.js` 的 `wx.uploadFile` 未接入 `UploadTask.onProgressUpdate`；UI 仅有“上传中/完成”等文字，无百分比、取消、明确重试。换胎上传/识别失败可能留下过期状态，费用上传失败保留路径可再点但没有明确“重试”，审批动作上传失败则与动作失败合并。后续应统一媒体任务状态机 `未选/待上传/上传中/成功/失败可重试`，明确文件名/缩略图、弱网等待、重复选择后的旧附件状态；OCR 无候选允许人工确认，不伪造匹配成功。

### 4.4 弱网、Loading、Error、Empty

请求封装对非 2xx 和网络失败弹 Toast，但多数读页面无可见 Loading、持久错误或手动重试。首页 `/me` 失败可能显示旧数据，线路/工资/审批列表失败可能与“暂无数据”同时出现。长流程提交时应防二次请求；发车没有 `busy`，重量确认弹窗中的 `loading` 过早结束，换胎上传/OCR 也未锁定并发。401 重定向有实现；403 不应仅短暂提示“无权访问”，应说明当前角色/绑定/权限条件。空状态至少区分：无任务、筛选无结果、无权限、请求失败。Toast 可作即时提示，但关键业务失败应留在页面上。

### 4.5 视觉一致性与户外阅读

全局 `app.wxss` 的页面背景 `#f4f6f8`、白卡、低饱和青绿主色方向适合保留；但功能卡、输入、Tag 大量重复相同白框，页面层级不鲜明。`.muted` 为 **24rpx**、`.tag` 为 **22rpx**，在常见 375px 逻辑宽度下约等于 12px/11px；户外强光、手持距离较远时存在可读性风险（需真机测量）。Tag 和按钮仅用统一样式，状态语义与错误/警告不系统对应。`.row` 最小高度 **56rpx**，用于图片、候选等点击行时约 28px，低于建议触控目标；通用按钮由微信默认样式决定，需真机逐个量测。当前各页纵向卡片没有桌面表格或明显横向布局，但多明细/审批 JSON 会造成过长纵向滚动，不能仅靠缩字解决。

## 5. 建议的信息架构（仅设计）

```text
工作台
├─ 当前车辆与绑定状态
├─ 当前/下一条线路（状态、下一步主操作）
├─ 待办（仅实际有权限且可处理）
└─ 次要入口（工资、换胎、费用申请、个人信息）

我的线路
├─ 待发车 / 运输中 / 已完成
└─ 线路详情 → 发车 / 重量录入并卸货

审批
├─ 我的申请
├─ 待我处理（仅非司机审批人）
├─ 已处理
└─ 费用申请 → 模板 → 明细/证据 → 摘要

换胎
└─ 拍照 → 识别 → 确认胎号 → 匹配库存 → 申请摘要

我的
├─ 账号/当前车辆
├─ 本人工资（仅自有司机且获权）
└─ 账户安全/退出
```

这是页面与任务层级，不要求每个分支都占固定导航位。外协司机的导航只显示其实际可用能力；权限或绑定不足时明确显示原因与下一步联系路径。线路任务卡是司机高频主入口；审批处理则服务非司机角色，不能强加给所有司机。

## 7. 小程序 Design Tokens 建议（仅提案）

建议值供后续原型与真机对比度/触控验证，不在本轮落地。以 `rpx` 为单位，750rpx 设计宽对应常见 375px 逻辑宽时约 2rpx = 1px；具体设备仍须实测。所有页面共享，不能各页自定视觉。

| Token | 建议尺度与语义 |
|---|---|
| Typography | 主体 `28–30rpx`，关键信息 `32–36rpx`，页内标题 `36–40rpx`，金额/当前任务可更大；辅助文字尽量不低于 `26rpx`，户外关键状态不能用 22rpx 小灰字 |
| Spacing | 8rpx 基准，`8/16/24/32/40`；卡内 `24–32rpx`，字段间 `24–32rpx`，任务组间 `32–40rpx`；避免无限白框堆叠 |
| Touch | 主要按钮和可点行目标至少约 `88rpx` 高；按钮间距约 `16rpx`，底部主动作适配安全区；mini 控件须有扩大的点击区域 |
| Radius/Border | 卡片约 `12–16rpx`，输入/按钮 `10–12rpx`；1rpx 柔和边线只在输入、分区处，避免粗重描边 |
| Shadow/Surface | 浅中性页面背景、近白任务卡；普通卡无或极轻阴影，只有浮层使用明显层级；不使用大面积渐变/玻璃拟态 |
| Primary | 沿用低饱和青绿色，只给当前步骤主操作；次要动作使用文字/浅底而非同权实色 |
| Success/Warning/Danger/Info | 完成/待办/危险/信息各有稳定浅底+深色文字；同时配中文文字或图标，不靠颜色独自表达 |
| Text/Disabled | 正文深中性；次级灰需满足户外可读性，对重要线路/重量/金额不用弱灰；禁用要可辨并解释原因 |
| Number/Date | 金额固定币种和两位小数，重量固定单位与精度，日期为用户熟悉格式；内部枚举、ID、JSON 不作为主要文案 |
| Motion/Feedback | 仅短促状态过渡；请求超过短暂延迟显示进度/骨架，图片上传可见进度与重试；避免装饰动画消耗注意力 |

验收时至少覆盖常见 iPhone/Android 尺寸、底部安全区、不同字体设置、户外强光和模拟弱网；不得因增加留白而把一趟线路的主动作推到多屏之后。

## 8. P0/P1/P2 页面问题矩阵

每行是一页的最高优先级主问题；`P0/P1/P2` 数量仅统计这一列。其他风险已在各页和全局章节展开。

| 页面 | 主问题及证据 | 对司机的影响 | 建议目标结构 | 优先级 |
|---|---|---|---|---|
| 登录 | 请求失败仅短 Toast、无字段内解释，提交无显式防重 | 弱网下不知重试还是改密码 | 单页登录+内联错误 | P1 |
| 首页 | 两列功能宫格代替当前任务/下一步，`loading` 未呈现 | 多点几层才能开始高频动作 | 当前车+任务卡+少量入口 | P1 |
| 个人信息 | 改密与资料常驻、司机类型原始码 | 查车牌时被低频表单干扰 | 摘要+账户安全子页 | P1 |
| 我的线路 | 只取前 50 条再本地筛选，无分页 | 超过 50 条时可误报“暂无线路” | 状态任务列表+服务端分页 | P0 |
| 线路详情/发车 | 返回卸货页后不刷新、发车无防重/按钮权限校验 | 旧状态诱发重复操作或可点后 403 | 状态驱动详情+单一主动作 | P0 |
| 卸货称重 | Modal 回调未等请求结束，`loading` 提前清除 | 弱网中可重复点卸货，结果不确定 | 重量摘要+受控确认 | P0 |

**统计：11 页；P0 6，P1 5，P2 0。** 视觉细项虽多，但当前每页都有更高优先级的任务/信息问题，故没有以纯 P2 作为页面主问题。

## 9. 页面重构分批建议（仅排期）

1. **批次一：状态、权限与移动底座。** 统一中文状态/错误/加载/空态、触控与底部安全区、首页任务式入口；核对 `isDriver` 与后端精确角色判定。先消除页面可见但后端必拒绝的动作。风险：菜单权限与司机类型必须保持后端 Policy 红线。
2. **批次二：线路高频闭环。** 我的线路真实分页、详情刷新与状态驱动操作、发车/卸货提交锁、重量单位和摘要。风险：不能改变既有发车/卸货业务规则；用自有及外协账号实际验证。
3. **批次三：换胎与 OCR。** 拍照/上传/识别/确认/库存匹配分步，当前车不可误改，上传进度和弱网重试。风险：不能绕过 OCR 确认、`request-target` 与创建时二次库存校验。
4. **批次四：审批、费用、工资与账户。** 业务可读的申请/审批时间线、多明细费用步骤、工资真实汇总口径、个人页低频操作。风险：Submission 版本证据、审批动作与工资计算必须保持；未获得完整数据时不显示虚假的合计。

每批上线前在真机与弱网下回答：我现在执行哪件事、下一步是什么、提交后产生什么结果、失败可否继续；再核对自有/外协的不同权限。不能以隐藏错误、隐藏业务状态来制造“简洁”。
