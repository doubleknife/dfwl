# R7-BIZ-1 V2 评审决策冻结记录

> 本记录是后续 BIZ-1A～1D、BIZ-1R、R7-UI-FIX 的唯一业务决策基线。旧版 R7-BIZ-1 及与本文冲突的早期口径全部废弃。出现新冲突必须停止并标记 DECISION REQUIRED。

## 1. Driver / User
- `Driver.driverType` 是 INTERNAL / OUTSOURCED 唯一权威来源，不从车辆绑定、Role、工资或线路反推。
- DRIVER 系统角色与 driverType 是两个维度。
- 系统管理→用户不得人工创建/分配 DRIVER。
- 司机只能从基础资料→司机创建/维护，由司机业务流程创建或关联 User 并建立 DRIVER 身份。
- driverType 变更必须结合车辆绑定、未完成线路、工资/历史事实做专门约束。

## 2. 车辆边界
- INTERNAL 使用公司 vehicle 与正式司机车辆绑定，保持既有公司车辆校验。
- OUTSOURCED 永远不绑定公司车辆；绑定候选排除且后端 bind API 强制拒绝。
- OUTSOURCED 不创建 company vehicle/binding、不要求 vehicleId；车牌只作为线路参与事实。
- 外协车牌不校验存在、归属、保险、绑定或车辆状态；不同线路/参与阶段可不同车牌。

## 3. 线路参与模型
- 一条 Route 支持 N 个有序参与记录及任意次数转派，禁止 first/second driver 一次性设计。
- 参与记录需追溯顺序、司机、司机类型事实、INTERNAL vehicle 或 OUTSOURCED plate、工资、INITIAL/TRANSFER、指派/发车/结束时间、结束方式、转派原因及必要快照。
- 历史不得通过覆盖 route_task 当前司机/车辆而丢失。

## 4. 初始工资
- 第一次线路只有一个司机，该司机是第一参与记录，其线路工资就是第一笔参与工资。
- 无转派时线路工资即第一参与司机有效工资。
- OUTSOURCED 初始线路发布同样必须具备外协车牌和工资。
- 普通未执行指派合法取消时不形成有效工资。
- 一旦转派，转派动作重新核定全部既有参与工资并填写新参与司机工资。

## 5. 取消、转派
### 普通取消
- 只适用于尚未进入转派链的未执行普通指派。
- 取消后可重新指派；该取消指派不产生有效工资和车辆费用资格，但保留历史。
- 一旦首次正式转派，后续换司机即使当前接手人没点发车，也不得再普通取消，只能继续转派。

### 转派
- 发车后允许通过正式转派动作换司机/车辆；普通编辑仍不得覆盖发车后事实。
- 转派由角色权限控制，不写死 ADMIN。
- 转派封存上一阶段并创建新当前参与记录；新司机需要重新点击发车。
- 是否点击发车不决定转派工资或 INTERNAL 车辆费用资格。
- 未发车又换人时继续转派；模型支持 N 次。
- **转派过程中不允许作废，货物必须最终完成卸货。**

## 6. 转派工资与独立工资调整
拥有“线路转派”权限者转派时：
- 可重新核定所有已有正式参与人员工资；
- 可将工资调整为 `0.00`；
- 不得删除参与记录；
- 新参与司机工资必填；
- 转派原因必填；
- 仅金额变化才写工资调整历史。
该能力属于转派本身，不额外要求独立工资调整权限。

另设“线路工资调整”权限，用于非转派场景修改任意参与工资（含 0）。原金额、新金额、原因、操作人、时间永久留痕；普通线路编辑不得绕过。
线路工资 = 所有纳入有效参与口径的参与记录当前有效工资之和。

## 7. 参与时间窗口与多车辆费用资格
- 同一线路所有正式参与司机/车辆共享整条线路发车～卸货时间窗口，不按转派时间切段。
- INTERNAL 正式参与车辆具有该线路费用资格，与是否点击发车、工资是否为 0 无关。
- OUTSOURCED 车辆永远不能申请/产生公司线路车辆费用。
- 混合线路只允许 INTERNAL 公司车辆产生费用。
- 选择线路后，费用车辆候选仅返回该线路符合资格的 INTERNAL 公司车辆；后端提交/落账再次校验。

## 8. 费用自动归属与重新分配
自动归属条件：
1. 公司车辆属于该线路正式 INTERNAL 参与车辆集合；
2. 费用业务时间位于整条线路发车～卸货时间；
3. 唯一匹配才自动归属。

0 匹配→未归属；1 匹配→自动归属；多匹配→不猜，进入未归属/待确认。外协车牌不参与公司费用自动归属。

所有正式费用（自动归属的导入费用、审批落账、合法人工录入）都允许有权限角色重新分配线路：
- R001→R002；
- R001→未归属；
- 未归属→R002。
必须记录原线路、新线路、操作人、时间、原因，优先复用 ExpenseAttributionHistory。
归属变化立即改变相关线路费用和利润，但单纯重新归属不改变公司已发生的总费用。

## 9. 未归属费用与公司总核算
“费用真实发生”与“费用归属于哪条线路”是两个事实。
- 未归属费用不进入具体线路支出/线路利润。
- 但有效未归属费用必须进入公司总支出/公司总利润口径，不能因未找到线路而让公司利润虚高。
- 公司总利润聚合必须避免已归属、未归属、日常费用等重复扣减。
- 费用归属调整只改变线路之间的成本分布；R001→R002、R001→未归属、未归属→R002本身不改变公司总费用。

## 10. 最终卸货与磅单（P0）
- 转派线路最终必须由当前有效参与司机完成卸货；历史已转派司机不能完成同一路线。
- 最终必须有一辆当前参与车辆/司机完成卸货，线路才能 COMPLETED。
- INTERNAL/OUTSOURCED 小程序卸货都必须上传至少一张合法磅单；无磅单前后端均拒绝完成。
- 磅单进入正式 Attachment，绑定本次卸货/原始重量事实，保留上传人/时间。
- 后续重量调整不得覆盖原始司机磅单，可另附调整依据；附件必须有权限控制。

## 11. 达标与司机端脱敏（P0）
- INTERNAL 后台继续计算 TRUE/FALSE。
- OUTSOURCED 目标语义为 `NULL = 不适用`，实施时按评审确认历史兼容。
- 达标率分母只统计适用记录。
- 所有司机端均不显示达标、达标率、阈值；未达标不阻止卸货。
- INTERNAL/OUTSOURCED 司机线路 API 均不得返回线路单价、本趟/参与/外协工资、线路收入、线路/公司利润、达标结果/阈值。
- 必须从司机专用 DTO/契约移除，不只前端隐藏；`salary:mine` 正式工资单保留。

## 12. 作废与恢复
- **只有已经完成卸货、状态为 COMPLETED 的线路才允许作废。**
- 未发布、等待发车、运输中、等待接手等均不能作废；运输途中问题必须转派并最终卸货。
- 作废由独立权限控制，原因必填。
- UI 必须明确提示并要求勾选确认：作废后该线路全部经营数据不再进入当前有效线路经营统计，包括线路收入、所有参与司机工资、所有归属于该线路的费用（含审批落账、导入、人工录入）和线路利润。
- 作废不删除重量、磅单、参与司机/车辆、工资、费用、审批、归属历史、状态历史。
- 线路作废不应让公司真实发生的费用凭空消失；公司总费用/总利润仍遵循“费用真实发生与线路归属分离”的公司口径。
- VOIDED 重新启用固定恢复 COMPLETED，因为只有 COMPLETED 能作废。
- 旧月结版本不变；新版本需有独立 ROUTE_VOID / ROUTE_REACTIVATE（最终命名按规范）差异语义。

## 13. 线路导入拆分
### 新线路导入
Preview/Commit 后进入正常新线路状态机，可发布、发车、转派、卸货。

### 历史线路导入
用于补录系统上线前已真实完成线路：
- 导入后直接是 COMPLETED 历史事实；
- 不得重新发布、发车、转派、卸货或作为新线路再次执行；
- 可查看、进入历史经营数据/报表/月结；
- 可按 COMPLETED 规则谨慎作废；
- 必须保留 HISTORICAL_IMPORT 等来源标识及 ImportTask/Row 追溯。
历史模板字段后续按真实模板冻结，不得臆造事实。

## 14. 已完成线路列表与完整经营档案
已完成线路列表直接显示：线路号、日期、客户、参与司机摘要、参与车辆摘要、净重、达标/不适用、**收入、总支出、利润**、操作。

口径：
`收入 = 最终有效重量 × 含税单价`
`总支出 = 当前有效线路费用净额 + 当前有效参与工资合计`
`利润 = 收入 - 总支出`

详情显示完整数据：概况、N次参与/转派、重量、原始磅单、各参与工资及调整历史、各 INTERNAL 车辆费用、收入、总支出、利润、支出构成、费用明细、状态/操作历史。
列表看总计，详情看完整组成。金额按经营/财务权限控制。

## 15. 月结
旧 Settlement Snapshot 永不修改。
后续 UI：`经营看板 → 版本明细 → 与前版差异`。
- 看板：收入、总支出、利润、支出构成。
- 明细：线路经营、线路费用、日常费用、司机工资。
- 差异用业务语言解释工资调整、重量调整、费用新增/冲销、费用归属调整、线路作废/恢复等。
- 每条差异尽量提供业务对象、原/新值、操作人、时间、原因及收入/支出/利润影响。
- 原始 JSON 只放高级信息。

审批来源费用在月结只需展示：发起日期、费用类型、金额、发起人、最终通过人、通过时间；不要求一路钻入完整审批。

## 16. 审批详情与打回
审批详情后续 UI-FIX 改为业务单据/表格型：结构化摘要、申请明细表、申请说明/依据、紧凑审批动作表；JSON 默认隐藏；操作按钮统一居中，主操作为“打回 / 通过”。

“打回指定节点”正式定义为“打回指定步骤”：
- 目标是冻结流程版本中的具体 Step/Node，不是岗位、角色或审批人；
- 同一岗位/审批人出现多次时必须明确第几步；
- 只有当前实例存在合法可返回的前置步骤时才显示“打回指定步骤”；
- 没有可返回步骤时只允许打回申请人；
- UI 显示 `第N步 · 步骤名称 · 审批人（辅助）`；
- 用户不得手填节点序号；
- API 使用稳定 Step/Node ID，后端校验合法性；
- 打回与重新流转新增 Action 历史，不覆盖第一次流转；
- 若有条件跳过节点，以当前实例实际合法可返回步骤为准。

## 17. 费用管理与费用导入
- 费用管理必须支持按**具体线路**筛选，使用可搜索业务选择器，不输入 routeId。
- 线路筛选展示当前有效归属于该线路的正式费用；归属调整后列表与线路核算同步变化。
- 费用导入不再假设“万能费用 Excel”。用户后续会提供所有真实费用模板，再单独冻结来源、类型、列映射、时间/车牌/金额字段、唯一键和自动归属。
- 在真实模板提供前，不虚构充电/ETC/油卡等解析器。

## 18. 历史迁移
- 无法可靠推断的旧历史事实绝不猜。
- 历史外协缺车牌、driverType 曾变化、旧脏绑定等可标记“历史资料不完整”，不因无法推断而伪造。
- 只读历史和旧月结继续可追溯。
- 仍需继续执行的新业务记录，在执行新动作前必须补齐新规则要求的真实信息。

## 19. Audit Log（P0）
评审已确认 audit_log 当前只有查询证据，不能把“有日志页面”当成“关键动作已统一审计”。
后续必须建立实际写入底座，至少覆盖：
- 转派；
- 转派时工资重核；
- 独立线路工资调整；
- 作废/重新启用；
- 费用重新归属；
- 必要的重量/经营高风险调整；
- 角色权限等高风险变更。
记录至少能回答谁、对象、原值、新值、原因、时间。专项历史表继续保留，不另建第二套审计系统。

## 21. 实施阶段
