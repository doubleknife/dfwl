# 审批模板版本化配置（R7-3F3C）

`approval_template` 保存稳定的 `template_code`、类别和既有 `approval_type`。`approval_flow` 的每行仍是一个具体版本；`approval_instance.flow_id` 始终引用发起时的历史版本。名称、节点、申请依据、允许发起角色和费用配置属于版本，不覆盖旧版本。

模板类别为 `TIRE`、`EXPENSE`、`OTHER`。管理 API 可创建 `EXPENSE`、`OTHER`，也可创建代码为 `TIRE_REQUEST` 的 TIRE 模板；TIRE 申请仍从换胎专用入口发起。EXPENSE 版本仅记录现有 `ExpenseType`、`SINGLE/EXCEL` 录入方式和 `ROUTE/DAILY` 归属选项。Excel 只代表后续前端本地录入能力，不在服务端存储文件或解析。

首版创建会在一个事务里写入 Template、DRAFT Flow V1、节点、发起角色及适用的费用配置，不自动发布。维护沿用现有 `ACTIVE → MAINTENANCE → 新 DRAFT 版本 → 发布` 路径；版本号按 `template_id` 独立递增。发布锁定模板行，数据库生成列的唯一索引进一步保证每个模板最多一个 ACTIVE 版本。不同 EXPENSE 模板可以同时 ACTIVE。

V3 对旧 Flow 按 `approval_type` 建立一个稳定模板，`template_code` 取原 `approval_type`，不改旧 Flow 或 Instance ID。旧 `TIRE_REQUEST` 归 TIRE、旧 `EXPENSE` 归 EXPENSE，其他无法确定的类型归 OTHER。历史发起角色和费用选项不能从旧数据可靠推断，因此保持空值并标记 `NEEDS_REVIEW`；旧附件行为对应 `OPTIONAL`。旧的按 `approvalType` 创建入口只选择代码等于该类型的历史兼容模板，不会在多个新 EXPENSE 模板之间任意挑选。按 `templateId` 发起和版本角色强制校验留待 F3D。

新管理接口见 `openapi.yaml` 的 `/approval-templates`。旧 `/approval-flows` 管理接口保留以兼容现有管理端；其维护操作现在按模板判定在途实例并创建模板内新版本。费用多明细、Excel 后端上传、TIRE 原图进入 Submission 均不属于本阶段。

## F3D 发起与重提契约

通用发起先查询当前用户可用的 ACTIVE 且配置完整的 EXPENSE/OTHER 模板，再以 `templateId` 明确选择版本。服务端按模板身份锁定 ACTIVE Flow，校验 `approval:create`、该版本允许的角色、申请依据和费用归属；自有司机还必须通过车辆及线路资源范围校验，外协司机不得发起费用审批。TIRE 继续经换胎专用入口，以固定 `TIRE_REQUEST` 模板身份定位版本。

旧客户端不传 `templateId` 时，仅在原 `approvalType` 对应的历史模板是该类型唯一 ACTIVE 模板的情况下保留旧的非司机发起行为；多个同类型模板同时 ACTIVE 时拒绝猜选。历史 `NEEDS_REVIEW` 配置不提供给新模板选择入口，旧申请仍按既有兼容规则运行。申请依据 `NONE` 不强制附件，且为兼容原有上传行为允许额外合法审批依据；`OPTIONAL` 允许零到多份；`REQUIRED` 至少一份。附件仍按上传人、用途及临时归属校验。

重提只允许原申请人，始终按 `approval_instance.flow_id` 的原版本校验依据、角色与费用配置，不切换当前 ACTIVE 版本；司机当前身份和资源红线仍重新校验。审批详情的版本配置也从该历史 `flow_id` 读取。仍在 `PENDING` 的审批阻止模板维护；已退回申请人、没有待办任务的旧实例允许模板创建新版本，并可按原版本重提。EXPENSE 仍只处理现有单条费用；多明细留待 F3E，TIRE 原图证据链留待 F3F。
